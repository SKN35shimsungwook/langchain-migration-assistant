#무엇근거 (이번 실행)담당개선안
1코드 변환 요청이 'LangChain 질문(search)'으로 분류됨1.x로 올리기 30개 중 6개(q06 · q07 · q09 · q20 · q26 · q28). 코드와 함께 '에러 이유', '무엇을 설치', '어디가 바뀌었는지'를 같이 물으면 '고쳐 주세요'가 있어도 search. 3번 반복해도 같은 결과라 우연이 아니라 규칙 문제1번① 분류 규칙에 '코드가 있고 고치기 · 바꾸기 의도가 있으면 설명 요청이 섞여도 migration' 추가, classifier temperature 0.7 → 0 (6개가 바로 변환 경로로 → 최종 통과 약 67% 기대)
2기록 없는 변경(환각)이 가장 흔한 실패 원인모든 시도의 오류 중 1위 unrecorded_change 33회. 최종 실패 11건 중 9건에 포함. 1회차 실패 후 다시 시도해 통과한 비율 31%(5/16)3번 · 1번② rewriter 프롬프트에 '요청 코드에 없던 줄 · 문서 예시 코드를 새로 넣지 말 것' 명시, 환각을 만든 근거도 다음 시도에서 제외(EVIDENCE_FAULT_TYPES에 unrecorded_change 추가) (검사기가 막고 있어 '통과'로 나간 환각은 없음)
3바꾼 줄에 근거 ID를 안 붙임missing_evidence 23회(전체 시도). 최종 실패 4건(q13 · q14 · q23 · q24)3번② 출력 형식에서 evidence_ids를 필수로(빈 목록이면 구조화 출력 단계에서 거절), 재시도 피드백에 '어느 근거를 붙이면 되는지' 후보 제시
4검사기 빈틈 ①: LCEL 결과를 ['text']로 꺼내는 코드를 통과시킴q10: result = chain.invoke(...) 다음 줄에서 result["text"] (실행하면 TypeError). 10번 검사는 chain.invoke(...)["text"]처럼 한 줄에 쓴 경우와 llm 변수로 끝나는 체인만 봄3번③ 결과를 변수에 담은 뒤 꺼내는 경우, 체인 끝이 ChatOpenAI(...) 직접 호출인 경우까지 검사 (eval/score.py의 lcel_subscript와 같은 방식)
5검사기 빈틈 ②: 목표 버전을 보지 않고 항상 1.x 기준으로 검사q32: 0.x로 되돌려 달라는 요청에 1.x 전용 create_agent를 쓴 코드가 '검증 통과'. 버전 오가기 6개 중 정답 import를 맞춘 답 0개3번 · 2번③ verifier가 state의 target_version을 받아 2번 version_resolve(버전별 도구 목록)로 import 존재를 확인
6최신 방식 대신 langchain_classic으로 우회q15(RunnableBranch 대신 MultiPromptChain), q21(체크포인터 대신 ConversationBufferMemory), q22(create_agent 대신 initialize_agent). 실행은 되지만 '지원 종료 예정' 경로2번 · 3번④ retriever가 대안(alternative) 사용법 문서를 함께 찾도록, rewriter는 classic으로 우회하면 notes에 '최신 방식 아님 + 대안'을 반드시 적기
7속도는 목표 안코드 변환 중앙값 11.6초(최대도 60초 이내), 일반 LLM 3.5초. 다시 시도가 붙으면 30초 안팎-화면의 진행 단계 실시간 표시로 기다림 체감 줄이기 (적용 완료)

5. 프로젝트 의의

  1. 모델을 바꾸지 않고 신뢰를 만든다: 같은 gpt-4o-mini가 혼자서는 0%, 근거 + 코드 검사 + 재시도를 붙이면 57%(실행 기준 87%).
  2. 버전 지체 환각을 실제로 재현하고 막았다: 일반 LLM은 옛 코드를 '수정했다'고 돌려줬고(29/30), 챗봇은 검사로 걸러 실패를 알렸다.
  3. 틀릴 때 틀렸다고 말하는 AI: 답마다 근거(93%)와 검사 결과를 보여 줘 사용자가 직접 확인할 수 있다.
  4. 스스로 점검하는 구조: 팀 규칙 21가지를 실행 기록으로 채점하는 도구로 고칠 곳과 순서를 데이터로 정했고, 개선 후 같은 도구로 효과를 다시 잰다.
  5. 확장성: 대응표 · 문서 · 검사 기준만 바꾸면 빠르게 바뀌는 다른 라이브러리(pydantic, OpenAI SDK 등)에도 같은 구조를 쓸 수 있다.

6. 한계

  • 질문마다 1회 실행입니다. LLM 답은 매번 조금씩 달라서 몇 %p는 오르내릴 수 있습니다 (분류만 3회 반복).
  • 채점은 코드를 실제로 실행하지 않고 정적으로 확인합니다 (문법 · import 존재 · 이름 · 결과값). 실제 실행 결과가 맞는지는 확인하지 않았습니다.
  • '정답 import 포함'은 질문마다 한 가지 정답 기준이라, 다른 올바른 방법도 감점될 수 있습니다. 그래서 정답 import를 뺀 '실행 기준 통과'도 함께 표시했습니다.
  • 일반 LLM은 시스템 프롬프트 없이 그대로 물었습니다 (ChatGPT에 붙여 넣는 상황). 프롬프트를 잘 쓰면 더 나아질 수 있습니다.
  • 질문 30개는 팀이 직접 만든 것이고, 버전 오가기 6개는 표본이 작아 참고용입니다.
  • 자체 평가의 목표치는 4번이 실무 기준으로 정한 값입니다. 팀 합의로 조정할 수 있습니다.
